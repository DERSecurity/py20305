**The operations history is safe to read while readings arrive, and its file is readable by its owner only (#72).**
The interval part kept its unfinished intervals in memory with no lock, so a
query on a management API thread could fail with "dictionary changed size during
iteration" while the event loop recorded a reading, and an interval that ended
between a query's database read and its look at memory could be missed. The
running sums are now guarded by a lock held only for in-memory work. Each
process writes its intervals as its own rows, tagged with a per-process `boot`,
and a query adds an unfinished interval from memory only when this process has
not written it yet, so an interval ending during a query is counted exactly
once. Rows written by 0.14.0 are moved into the new `interval_rows` table when
the history is opened. A read now waits only for the writes queued before it,
so a steady stream of writes cannot hold a read off. The history file is
created 0600 and a directory created for it 0700, as the connection logs of
the products that use it are, and an existing file is tightened to 0600; SQLite
gives its journal files the same mode.
